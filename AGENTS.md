# Repository Guidelines

## Project Structure & Module Organization

This repository is a Quarto portfolio website. Top-level `.qmd` files define the main pages: `index.qmd`, `projects.qmd`, `art.qmd`, `blog.qmd`, and `podcast.qmd`. Site configuration lives in `_quarto.yml`; shared styling lives in `styles.css`, with page-specific styles in files such as `projects.css`, `art.css`, and `design.css`.

Long-form content belongs under `posts/`, grouped by topic: `posts/machine_learning_projects/`, `posts/publications/`, `posts/full_stack/`, and `posts/learning/`. Static assets live in `images/`, `assets/`, and `code_files/`. `_site/` is generated by Quarto and should not be hand-edited.

## Build, Test, and Development Commands

- `quarto preview`: serve the site locally with live reload.
- `quarto render`: build the full site into `_site/` and catch broken Quarto syntax, missing files, and notebook render failures.
- `quarto render projects.qmd`: render a single page during focused edits.

GitHub Pages builds run through `.github/workflows/quarto-publish.yml`, which installs Quarto `1.8.24`, runs `quarto render`, uploads `_site/`, and deploys on pushes or pull requests targeting `main`.

## Coding Style & Naming Conventions

Use concise Markdown and Quarto syntax in `.qmd` files. Keep YAML front matter valid and minimal. Prefer relative links, for example `posts/publications/graphrag-crs.qmd`.

Use lowercase, hyphenated filenames for new posts and assets, such as `posts/publications/encoding-values.qmd`. Existing legacy filenames may use mixed case; do not rename them unless links are updated everywhere. Keep CSS readable with two-space indentation and page-scoped selectors when possible.

## Testing Guidelines

There is no separate unit test suite. Treat `quarto render` as required validation before submitting changes. After edits, inspect the rendered page in `_site/` or via `quarto preview` to confirm navigation, images, code blocks, and publication/project links work.

For notebook-backed pages in `posts/learning/` or `code_files/`, confirm the notebook renders cleanly and does not require unavailable local secrets or credentials.

## Commit & Pull Request Guidelines

Recent commits use short, imperative summaries such as `Refresh portfolio projects and publications` and `Pin Quarto version for Pages deploy`. Follow that style: describe the visible change in one line.

Pull requests should include a brief description, affected pages, validation performed (`quarto render` or preview), and screenshots for visual layout changes. Note generated `_site/` changes explicitly so reviewers can distinguish source edits from build output.

## Agent-Specific Instructions

Start content work from source files, especially `index.qmd` and `projects.qmd`. Do not manually edit `_site/`; regenerate it with Quarto. Preserve unrelated local changes, including generated files and system metadata, unless the user specifically asks for cleanup.
